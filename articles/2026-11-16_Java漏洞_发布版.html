Java 17 爆出 9.2 分高危漏洞，跑 ERP 的服务器该怎么查？

Oracle 11 月的 Java 补丁更新里，有一个被早期报告称为 CVE-2026-114938 的漏洞：无需认证即可远程执行代码（pre-auth RCE），CVSS 4.0 评分 9.2，影响 OpenJDK 17.0.6 及之后的版本（来源：《Pre-auth RCE flaw in Java 17》Aikido Security，2026-11-17；《Oracle Critical Patch Update》2026 年 11 月）。

对多数企业来说，这条新闻的问题不是"要不要紧张"，而是"我的服务器上到底跑没跑 Java，跑的是哪个版本"——很多公司答不上来。

一、为什么这条和用友/ERP 用户有关

用友 U8、T+、以及不少中间件和报表服务，运行时依赖 JDK。典型情况是：

  • 服务器上装的是随软件一起带的 JDK，版本停在采购那年
  • 从来没人单独维护过 Java，升级都靠"下次换系统时一起换"
  • 有的装在应用目录里，连"这台机器有没有 Java"都要翻半天

所以这条漏洞的真正风险点不在"Java 本身"，而在这类随软件附带的、没人管的运行时。

二、四步自查（今天就能做）

第一步：找出所有 Java。 Windows： wmic product where "name like '%%Java%%'" get name,version 再补一遍文件系统搜索 java.exe，因为随软件附带的 JDK 不会出现在已安装程序列表里。 Linux： rpm -qa | grep -i openjdk # 或 dpkg -l | grep -i openjdk find / -name "java" -type f -path "*/bin/*" 2>/dev/null

第二步：看版本号。 执行 java -version。落在 17.0.6–17.0.21 区间内的，属于这次报告点名的范围；Java 8/11/21/25 也都在 Oracle 11 月补丁的受影响清单里，不能只看 17。

第三步：看暴露面。 这些 Java 服务有没有端口直接对着公网？ERP 的 8080/8081、报表端口、远程管理端口，是最常见的暴露点。对外可访问 + 未打补丁 = 组合风险。

第四步：打补丁 + 验证。 Oracle 的指引只有一条：尽快应用 Critical Security Patch Update，官方没有给出配置层的临时规避方案。 注意：不一定等 Oracle——如果你用的是 Eclipse Temurin、Amazon Corretto、Azul Zulu、Red Hat 构建或 Linux 发行版包，各自厂商的修复版本号不一样，要按各自的公告升级。

三、三个容易踩的坑

坑一：只升级了"我装过的 Java"，漏了随软件带的。 判断标准很简单：把所有 java.exe / java 的路径列出来，逐个看版本。数量往往比你以为的多。

坑二：升级完不验证。 升完必须重启依赖它的服务，再跑一次 java -version 确认生效。很多事故是"补丁打了但服务还在跑旧进程"。

坑三：升级前没备份。 老 ERP 对 JDK 版本敏感，升级后可能出现加密狗、报表插件、老接口不兼容。先在测试环境验证，再动生产；至少确认账套和数据库有可还原的备份。

四、如果你不想自己动

这类"运行时排查 + 补丁验证"的工作，标准动作是：盘点 → 版本比对 → 暴露面收敛 → 测试环境验证 → 生产升级 → 复验。少一步都可能出事。

我们处理过不少"补丁打完了但服务还是老进程"的现场，也见过升级后报表打不开的情况——所以流程里"验证"这一步不能省。
